# Обновления Бродяги в реальном времени

Бот и API записывают публичный снимок отметок в `map_reports_outbox` одной
транзакцией с изменением голосов. Это очередь с единственным последним состоянием:
за время сбоя новые отметки заменяют старые, очередь не растёт. Снимок содержит
сервер, название точки, координаты, число подтверждений, версию и срок актуальности.
Имена пользователей и Discord ID в него не попадают.

В процессе `web_api.py` работает один фоновый отправитель. Каждые 200 мс он
проверяет локальный `PRAGMA data_version` SQLite; снимок читает при изменении базы.
Не связанные с отметками записи не вызывают публикацию. Изменения между проверками
объединяются. Запросы браузеров для обнаружения изменений не используются.

Отправитель делает подписанный HTTP POST в API карты. Оно атомарно сохраняет
снимок в Redis и публикует событие. Повторные и устаревшие версии не рассылаются.
Одна Redis-подписка на процесс ASGI обслуживает все его WebSocket-клиенты;
клиенты не создают отдельных Redis-подписок и не читают базу.

Подписка в браузере включена только при видимой вкладке и включённом слое.
При каждом подключении приходит последний снимок из памяти процесса карты.
Медленный клиент хранит не более одного ожидающего снимка и отключается при
зависшей отправке. Heartbeat раз в 25 секунд проверяет соединение; повторные
подключения используют увеличивающуюся задержку и случайный разброс.

При ошибке доставки отправитель повторяет запрос через 2–30 секунд, сохраняя
последнее состояние в SQLite. Независимо от числа посетителей один сверочный POST
раз в 30 секунд восстанавливает кеш после перезапуска/очистки Redis. Это служебная
сверка между серверами, а не опрос со стороны посетителей. Новая версия обычно
отправляется в пределах 200 мс плюс время сети и обработки; это не гарантия SLA.

Ежедневный сброс в 01:00 UTC также создаёт новую версию. Браузер дополнительно
очищает истёкшие отметки по `expires_at`, даже если связь с сервером потеряна.
Смена эпохи после создания новой базы позволяет начать нумерацию версий заново.
При восстановлении старого бэкапа той же базы с меньшей версией требуется
остановить отправитель и удалить ключ `brodyaga:reports:snapshot` в Redis карты,
затем перезапустить `profiles-api` и отправитель. Иначе защита от старых версий
намеренно не позволит откатить опубликованное состояние назад.

## Настройка и запуск

1. Создайте случайный секрет: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
   Запишите одинаковое значение `BRODYAGA_PUSH_SECRET` в `.env` бота и
   `profiles_backend/.env` карты. Для dev используйте отдельный секрет.
2. В `.env` бота укажите URL нужного окружения, например:
   `BRODYAGA_PUSH_URL=https://dayz-map.ru/profiles-api/internal/brodyaga/reports`.
   На другом сервере используйте HTTPS; Redis открывать наружу не нужно.
3. У карты пересоберите `profiles-api`:
   `docker compose up -d --build profiles-api` из `profiles_backend`.
   Существующие PostgreSQL и Redis пересобирать не требуется.
4. Опубликуйте изменённую статику карты. Убедитесь, что Nginx пропускает
   `/profiles-api/ws/` с WebSocket Upgrade. Если параметры таймаута изменялись,
   установите `proxy_read_timeout 75s;` для этого location. Heartbeat приходит
   каждые 25 секунд. Маршрут POST проходит через существующий `/profiles-api/`.
5. У бота выполните `docker compose up -d --build brodyaga-bot brodyaga-api`.
   Таблица очереди создастся автоматически. Отправитель запускается только в API,
   поэтому этот сервис должен работать, даже если отметки поступают из Discord.

Часы серверов должны быть синхронизированы: подпись запроса включает timestamp
с допуском 60 секунд. Неверная подпись отклоняется; секреты не передаются браузеру.

Для одновременной доставки в production и dev задайте в `.env` бота
`BRODYAGA_PUSH_TARGETS` — JSON-массив объектов `{"url":"...","secret":"..."}`.
Каждое окружение использует собственный секрет. Этот параметр заменяет одиночные
`BRODYAGA_PUSH_URL` / `BRODYAGA_PUSH_SECRET`. У каждого направления собственный
фоновый отправитель и повторы: недоступный dev не задерживает production.
Снимок и очередь SQLite общие, число отправителей не зависит от числа посетителей.

В DevTools браузера при включённом слое должно быть соединение
`/profiles-api/ws/brodyaga`, начальный снимок и новые сообщения после отметок.
Периодических `GET /brodyaga-api/reports` быть не должно. Старый GET сохранён
для совместимости и ручного обновления через `BrodyagaTrader.refreshReports()`.
После выключения слоя или скрытия вкладки WebSocket закрывается; после возврата
приходит актуальное состояние. Для проверки отказоустойчивости временно остановите
API карты, добавьте отметку через Discord и запустите API снова: состояние должно
восстановиться после повторной доставки и переподключения.

## Проверки

Бот: `python -m unittest discover -s tests -q`.

Карта, frontend: `node tests/frontend/test_brodyaga_realtime.js`.

Карта, backend (из `profiles_backend`, с `requirements-test.txt`):
`python -m unittest discover -s tests -p test_brodyaga_realtime.py -v`.

Проверяются транзакционная запись снимка, подтверждения, ежедневный сброс,
повторная доставка, HMAC, версии, подключение нескольких WebSocket-клиентов,
потеря Redis-кеша и ограниченная очередь на 10 000 подписчиков. Последнее —
проверка структуры очередей, не сетевой нагрузочный тест на 10 000 соединений.
